# 购物参谋 · 个人浏览器版（agentmart-browser）

> 版本 `1.0.0-browser` · 用**你自己的浏览器登录会话**在五个平台同台比价。

不需要任何电商开放平台资质。你在弹出的可见浏览器窗口里亲自登录，
Agent 在这一次任务范围内读取页面上的商品、价格、账号可见的优惠与售后政策，
组织成证据，算出到手价，横向比较京东 / 淘宝 / 天猫 / 拼多多 / 抖音商城。

**它是购物决策助手，不是代下单工具。**

---

## 硬性边界（代码层面强制，没有后门）

| 做 | 不做 |
|---|---|
| 弹出**可见**的浏览器窗口，你自己登录 | 不索取、代填、记录或上传账号密码 |
| 只读页面上的商品、价格、优惠、政策 | 不自动领券、关注店铺、发消息、加购 |
| 你随时可以暂停 / 接管 / 取消 | 不提交订单、不付款 |
| 价格必须与页面证据一致 | 不破解验证码、不绕过登录与风控 |
| 视觉识别与 DOM 证据冲突时丢弃视觉结果 | 不伪造请求来源、不做高频爬取 |
| 页面正文一律当不可信数据 | 不让页面内容影响 Agent 行为 |
| 登录态只存在本机 `~/.agentmart`（仓库外） | 不让模型收到 Cookie、完整登录态、支付信息 |
| 数据库只存任务记录 | 不存任何账号、Cookie、密码 |

## 快速开始

```bash
# 1. 后端（Python 3.11+）
python -m venv .venv
.venv/Scripts/activate        # Windows；macOS/Linux 用 source .venv/bin/activate
pip install -r requirements.txt
python -m playwright install chromium     # 装浏览器内核

# 2. 前端
cd frontend
npm install
npm run build
cd ..

# 3. 启动（一个端口跑完整应用）
uvicorn app.main:app --reload --port 8000
```

打开 http://127.0.0.1:8000 ，进「平台与模型」页：

1. **登录平台** —— 点对应登录组的「打开登录窗口」，在弹出的真实浏览器里
   自己扫码或输密码。淘宝和天猫共用同一个登录关系。
2. **填模型** —— 「平台与模型」页填你自己的模型 Key（BYO Key），
   先做一次连接与视觉能力测试，再设花费上限。
3. **开始比价** —— 回首页用自然语言说需求，选平台，开始。

> 没装 Playwright 内核时，服务照样启动、界面照样能浏览，
> 只有浏览器任务不可用，界面会明确说明缺什么。

## 五档价格确定性

不混淆「看到过」和「一定适用」：

| 档位 | 含义 | 是否计入到手价 |
|---|---|---|
| 页面公开 | 商品页明示、无需任何身份条件 | 计入「确定可算」 |
| 账号券 | 已确认在你账号下、且本次可用 | 计入「确定可算」 |
| 有条件 | 页面写了条件，未验证你是否满足 | 只计入「含待确认」 |
| 预付定金 | 预售定金 + 尾款结构 | 只计入「含待确认」 |
| 无法核验 | 只有宣传口径、没有可核验证据 | 不计入，单独列出 |

金额由确定性代码算，不让模型做心算。

## 优惠券树与双轨净价

页面上的优惠往往不止一条。两条规则保证算出来的价是你真能拿到的：

**同层互斥。** 每条优惠按文案推断归属层级（商品 / 店铺 / 平台 / 支付 / 补贴 /
运费）。同一层里的优惠只能选一个，取金额最高的那条 —— 两张店铺券不能都减掉，
否则界面写着到手 1169，结算页却要 1249。被挤掉的那条**仍然列在树上**，并写明是
被谁挤掉的，不悄悄消失。

**两个轨不混。** 公开轨只算谁来看都成立的抵扣；我的轨再加上页面显示你这个账号
已可用的券。跨平台比价看公开轨 —— 否则比出来的是账号差异，不是商品差异。我的轨
比公开轨便宜的那部分（`account_gap`）单独标出来，并说明"未登录时拿不到"。

多个层级同时抵扣时，能否叠加是按层级**推断**的，页面没有逐一说明，界面上会明确
写出这句话，并提示以平台结算页为准。

叠加关系的数据来源分两档，界面用 `stacking_confidence` 标注：数据源按平台公示规则
显式声明组名（`stack_group`）时是 `evidenced`，从文案推断层级时是 `inferred`。

> 优惠券由你自己在平台上领取。本工具不代领券、不代下单、不代付款，
> 也不把"页面出现过一张券"讲成"这张券一定适用"。

## 规格同步（同一个 SKU 才能比价）

标题相同不等于同一个 SKU。很多平台把颜色/尺码只放在规格选择器里，标题里不写 ——
标题完全一样的两件商品，一个选的是黑色 L、一个是蓝色 M。只看标题会把它们合成
一组，界面上出现一个 200 元的"平台价差"，而那 200 元其实是规格差。

因此规格文本和标题一起参与比对（`app/domain/sku.py`，前端镜像
`frontend/extension/core/sku.ts`）：

- **尺码、容量、版本（国行/海外）、成色（全新/二手）、套装与单品**不同是硬冲突，
  必须拆成不同商品组，不并进同一张对比表。
- **颜色不同**不拆组，但会标注 `variant` —— 价格仍然可比，界面上写明颜色不同。
- 归一化后再比：`曜石黑 L码` 和 `黑色 L` 是同一个规格，不该被拆开。
- 规格一个都读不到时是 `unknown`，不是 `matched`。读不到和一致是两件事，
  不能默认它俩一样。

每条报价带 `sku_sync`（matched / variant / unknown）和归一后的 `sku_spec`，
商品组带 `sku_status`。横向对比表和购买卡片都会标出来。

## 决策矩阵

比价不能只甩一个总分 —— 总分是黑箱，用户没法验证，也没法按自己的偏好重新权衡。
矩阵把每个维度单独列出来，每格给值和一句解释：

| 维度 | 说明 |
|---|---|
| 公开轨到手 | 只算谁来看都成立的抵扣。**跨平台比价看这一列** |
| 我的轨到手 | 含你账号下已显示可用的券，单独列示，不并进综合分 |
| 店铺与售后 | 店铺类型 + 平台级售后说明 |
| 数据新鲜度 | 24 小时内采集 / 采集时间较早 / 不是真实采集 |
| 规格同步 | 与组内基准是否同一个 SKU |
| 综合分 | 按当前权重加权：公开轨价格 + 店铺售后 + 数据新鲜度 |

权重随用户偏好切换（更看重价格 / 更看重售后 / 平衡），界面上把当前权重写出来，
用户能自己核对后改。

两条硬规则：

1. **综合分只用公开轨。** 我的轨含账号券，换个账号就没了。拿它排名，
   排出来的是账号运气，不是商品差异。
2. **规格不符的报价不能当赢家。** 它照常参与展示，但分数折损并标注原因 ——
   否则用户按矩阵下单会买到另一个规格。
