# 个人浏览器版（v1.0.0-browser）架构与验收说明

> 版本标识：`app/browser/__init__.py` → `VERSION = "1.0.0-browser"`，
> 与 API 架构版 `1.0.0-api` 相互独立，可分别封存、分别回滚。
> 两个版本共用同一套 domain 层（价格计算 / 优惠互斥 / 同款匹配 / 推荐规则 / 评测模型），
> 区别只在**数据从哪来**：API 版走平台开放接口，浏览器版走你本地的浏览器会话。

---

## 1. 这个版本解决什么问题

API 架构版的能力上限由「平台愿意开放什么」决定：没有开发者资质时，
个性化价格、账号可见优惠券、国补资格、店铺级售后承诺都拿不到。

个人浏览器版换一条路：**不依赖任何电商开放接口**，由你在官方页面自己登录，
Agent 在你发起的这一次任务范围内读取页面上的商品、价格、优惠与政策，
组织成证据，算出到手价，横向比较五个平台。全程你随时可以接管、暂停、取消。

它不改变一个前提：**购物决策由你做，账号由你自己登，券由你自己领，单由你自己下。**

```
  llm.py           自带 Key 的模型客户端：连接测试、视觉能力探测、用量与费用估算
  agent.py         编排器：状态机、五平台并发、预算/步数上限、取消、等待用户接管
  login.py         手动登录窗口：可见浏览器 + 只读登录探测，与任务对同一登录组互斥

  service.py       应用服务层（被 routers/browser.py 调用）

  pricing.py       到手价拆解：确定/潜在/待核验 + 公开轨/我的轨
  stacking.py      优惠互斥：同层取最优，不同层可叠加
  coupontree.py    优惠券树：按归属层级摊开，标出 counted / beaten_by
  models.py        Offer / Discount（layer、certainty）/ CanonicalProduct / Review
  matching.py      同款匹配与规格硬冲突
app/routers/browser.py   /api/browser/* 接口

```

数据流：

```
你的自然语言需求
  → parse_requirement（预算/类目/场景/地区/品牌）
  → ShoppingAgent.start（五平台并发，受 max_concurrency 限制）
      → 每平台：登录探测 → 搜索页 → 收集链接 → 逐商品读字段
      → Offer（带来源 URL、读取时间、证据定位）
  → group_offers（同款匹配，规格冲突不合并）
  → compute_price_breakdown（确定 / 潜在 / 待核验三档 + 公开轨 / 我的轨）
  → build_coupon_tree（按归属层级摊开，标出同层互斥与两轨归属）
  → recommend（综合首选 / 更省钱 / 更稳妥）
  → result_view → 前端购买卡片 + 横向对比 + 购买建议
```

这一版交付的是「可运行、可测试、可接管的任务框架 + 已用受控页面验证过的计算与状态机」。
真实平台验证需要你本人登录，那一步只能由你做。

## 4. 价格确定性四档（核心纪律）

| 档位 | 含义 | 计入到手价？ |
|------|------|-------------|
| 1 页面公开价 | 页面显示的标价/页面价 | 只说明页面显示多少 |
| 2 账号可见可用券 | 你账号里已领/可用的券，且页面显示它适用于该商品 | 计入「确定」 |
| 3 满足条件的预计价 | 门槛/适用范围/叠加规则都核对过 | 计入「潜在」 |
| 4 结算页待支付金额 | 结算页显示但未付款 | 需你确认，本版本不替你进结算页 |

任何一档核验不了 → `UNVERIFIABLE`，只列示、不计入。最终实际价格一律以原平台结算页为准。

代码里对应 `app/domain/pricing.py`：`definite_total` 只累计无条件成立的抵扣；
`potential_total ≤ definite_total`；演示数据（`DataStatus.DEMO`）不进入任何真实结论。

### 双轨净价与优惠券树

同一个到手价要回答两个不同的问题：「谁来看都该是这个价」和「我这次真正要付多少」。
混在一起答，跨平台比出来的是账号差异，不是商品差异。

- `public_total`（公开轨）只累计 `PriceCertainty.PAGE_PUBLIC` 的抵扣，跨平台比价用它；
- `account_total`（我的轨）= `definite_total`，再加上页面显示本账号已可用的券；
- `account_gap = public_total − account_total`，即账号权益带来的那部分，永不为负。

`app/domain/coupontree.py` 把一件商品上的优惠按归属层级（`DiscountLayer`：商品 / 店铺 /
平台 / 支付 / 补贴 / 运费）摊成一棵树，每条记录带 `counted` 和 `beaten_by`：同层互斥时
只有金额最高的那条 `counted`，被挤掉的仍然列出来并写明被谁挤掉。层级来源分两档，
`stacking_confidence` 标 `evidenced`（数据源按平台规则显式声明 `stack_group`）或
`inferred`（从优惠文案推断）；多个层级同时抵扣时界面必须提示"能否叠加是推断的"。

层级不明时（既没有 `stack_group` 也没有 `layer`）不进互斥组、单独成立 ——
这是唯一安全的默认，不会把两张券当成可叠加。浏览器版 `build_offer` 一定会填 `layer`，
所以那条保守路径在扩展侧不可达（`test_browser_offer_always_sets_a_layer` 盯着这件事）。

## 5. 安全与权限边界

**Agent 能做**：打开页面、读字段、滚动加载、截图取证、等你操作、就具体动作征求你同意。
**Agent 不能做**：领券、加购、关注店铺、发消息、下单、付款、代填账号密码、记录验证码、
识别或绕过验证码、伪造请求来源、高频抓取、隐藏自动化身份。

代码层面的硬保证：

- `ActionKind` 只有 `MUTATING` 一类会改变账号状态，编排器从不发出它；
- `/api/browser/*` 下不存在任何「领券/加购/下单/付款」端点，
  `test_only_allowlisted_endpoints_can_change_state` 会拦住新增的写接口（必须显式登记才会通过）；
- 每平台的暂停 / 取消 / 清除登录态都是单独端点，不存在「允许购物」这种一揽子授权；
- 模型接口永不返回 `api_key`；用量与费用只做估算并标注「不等于最终账单」；
- 落库内容只有任务快照与证据元信息（URL/时间/字段定位），
  **不存 cookie、登录态、截图原图、账号信息**；
- 页面上的商品文案、商家话术、评论区内容都是不可信输入，不会当作指令执行；
- 平台一旦阻止自动访问（验证码/风控/限频），该平台本次记为「受限」并停下，不用假数据补齐。

## 6. 浏览器登录态放在哪、怎么清

- 位置：`~/.agentmart/browser-profiles/<登录组>/`（可用 `AGENTMART_HOME` 改到别处），
  在仓库外，`.gitignore` 也已覆盖；
- 分组：京东 / 拼多多 / 抖音各一组，淘宝与天猫共用 `taobao` 组（同一套账号体系），
  但商品来源、店铺与结果在任务里仍然分开记录；
- 清除：设置页 →「平台与模型」→ 对应登录组的「清除登录态」，或
  `POST /api/browser/platforms/{group}/clear`；删除的是整个浏览器目录；
- 每次任务默认弹出**可见**窗口，你可以随时看着它在做什么；也可以设为无头（仅在你已登录且只想看结果时）。

### 跑任务之前，先在这个窗口里登录

比价任务默认无头运行、不能让你输账号，所以要先单独开一个登录窗口：

- 入口：首页或设置页 → 平台表格里的「登录」按钮，或
  `POST /api/browser/platforms/{group}/login`；
- 弹出的窗口是**可见**的普通 Chromium，直接停在该平台首页，
  账号密码、短信验证码、扫码都由你本人在这个窗口里完成；
- Agent 每 2 秒只探测一次「是否已登录」（一段只读 DOM 的脚本），
  **不读取、不保存、不上传你的账号、cookie、验证码和任何输入框内容**；
- 探测到已登录后窗口**不会**自动关，留给你自己关；
- 关窗口只是关浏览器，`~/.agentmart/browser-profiles/<组>/` 里的登录态保留，之后的比价任务直接复用。

登录态在界面上分五档如实显示，不把「目录存在」说成「已登录」：

| 状态 | 含义 |
| --- | --- |
| `none` | 这个组还没有任何登录态目录 |
| `saved_unverified` | 目录在，但本次没有探测到登录（可能已过期） |
| `waiting_login` | 登录窗口正开着，等你登录 |
| `logged_in` | 登录窗口里探测到已登录 |
| `failed` | 探测脚本本身出错 |

**互斥**：同一个登录组同时只能有一个 Chromium 持久化上下文。
登录窗口开着时该组不能开始比价任务（提示你「先完成登录并关掉窗口」）；
比价任务正占用该组时也打不开登录窗口。这是浏览器层面的限制，
代码里两边都做了显式检查和提示，不会出现两个进程抢同一个目录。
任务结束（完成/受限/失败/取消）时会主动收掉该组浏览器会话并释放目录，
不会出现"任务已经跑完，登录按钮还点不动"。

## 7. 自带模型（BYO Key）

在设置页「平台与模型」里填：provider、兼容端点 URL、模型名、Key、是否支持图像。
保存后先做一次连接测试与视觉能力探测：

- 探测方式：发一张 1×1 PNG 让模型描述颜色，据实判断；
- **不支持图像输入的模型不会被用来"看"网页**，只会走确定性 DOM 读取；
- Key 只写在本地 `~/.agentmart/model.json`，不进前端构建产物、不进 Git、不进普通日志；
- 删除入口：同一页的「删除本地模型配置」，或 `DELETE /api/browser/model`；
- 每个任务可设最大模型调用次数与最长时长，用完了就停，并展示已取得的证据，不会继续花钱。

**没有 Key 也能用**：应用照常启动、界面照常浏览、任务框架照常可跑，
只是不会调用任何外部模型（确定性 DOM 读取 + 规则计算仍然工作），界面上不会把它称作「真实 AI 浏览器购物」。

## 8. 成本可能来自哪里

- 你自己的模型 API 调用（按 token 计费）：只有页面结构变化、选择器失效或需要理解非结构化文本时才会调用，默认尽量走确定性 DOM 读取；
- 界面显示的是**估算**费用（按单价 × 用量推算），明确标注不等于最终账单；
- 不涉及任何本产品的付费服务，也没有会员、返利或佣金链接。

## 9. 平台使用规则与个人信息处理

- 只处理你主动发起的小额购物任务，不做后台持续批量采集；
- 不收集手机号、地址、订单记录、支付信息；
- 截图与日志默认脱敏，敏感区域不进模型上下文；要发给第三方模型的内容会在界面上说明范围，并可关闭；
- 各平台的服务条款与风控策略优先。页面或规则上走不通的能力，本版本选择停下并告诉你原因，提供「你手动贴链接/优惠信息/截图」的兜底路径，而不是绕过。

## 10. 测试怎么跑、覆盖了什么

```bash
python -m pytest                       # 351 passed（含 5 个真实 Chromium 端到端用例）
cd frontend && npm run build           # tsc --noEmit && vite build
cd frontend && npm run test:extension  # 216 passed（领域逻辑与扩展）
cd frontend && npm run build:extension # MV3 扩展打包
```

重点用例：

- 规格硬冲突不合并（容量/版本/成色/套装/品牌/尺码）；
- 优惠门槛、互斥组、叠加、过期、运费、国补资格不确定；
- **同层互斥**：两张同层店铺券只算金额最高的那张，被挤掉的仍列在树上并写明被谁挤掉
  （端到端用例 `test_same_layer_coupons_and_dual_track_flow_through_real_chromium`
  用真实 Chromium 断言到手价是 1179.00，不是把两张券都减掉的 1169.00）；
- **双轨净价**：公开轨只算谁来看都成立的抵扣，账号券只进我的轨，
  跨平台比价用 `best_public_price`；
- Python 与 TypeScript 两侧价格逻辑用同一份语料逐字段比对
  （`tests/test_extension_parity.py` ↔ `frontend/extension/tests/corpus/page-fields.json`）；
- 视觉金额与 DOM 证据不一致时被拦截；无 DOM 证据的视觉价格会被降级；
- 单平台失败不影响其它平台；验证码记 `restricted`；登录过期等你接管；
- 取消任务、预算耗尽都能安全停下并保留已取得的证据；
- 任务取消/结束后结果落库，服务重启后从库里回读（`restored` 标记，只能看不能继续跑）；
- 拼错 `/api/*` 返回 JSON 404，不会回退成 200 + 前端页面而让调用方误判成成功；
- 「要不要加入专业评测分析」只问一次：回答之后任务必须往下跑，不能又被问一遍
  （这个 bug 的真实表现是任务永远卡在第 2 步，一次都跑不起来，见
  `tests/test_browser_review_question.py`）；
- 登录窗口与比价任务对同一登录组互斥（两个方向都有用例）；
- 任务结束后浏览器会话被收掉、目录被释放，不会挡住之后的登录窗口；
- 登录探测脚本里不允许出现读 cookie / 输入框 / 密码的写法；
- 没有任何自动下单/付款路径。

端到端用例用 `app/browser/fixtures.py` 起的本地受控页面 + 真实 Chromium，
**不访问任何真实电商网站**。

## 11. 已知限制与下一步

- 五个平台都还没用真实账号跑通过（需要你本人登录）；配方与选择器会随平台改版失效，
  失效时该平台会记 `restricted`/`failed` 并说明原因，不会猜；
- 视觉模型只在选择器失效时介入，覆盖不了所有页面结构；
- 结算页核验（第 4 档）本版本不做，因为那一步接近「改变账号状态」；
- 下一步建议：先用京东单平台真实跑通并记录选择器有效期，再逐步开第二个、第五个平台；
  官方 API 资质到位后，数据接入层可切换（`app/adapters/` 与 `app/browser/` 都是可替换的数据源），
  domain 与前端不用改。
